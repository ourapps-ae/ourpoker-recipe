# OurPoker application-specific component

## Purpose and facilities
Package `ourapps-ae/ourpoker` version 0.4.1, kind `recipe`. It is the part of the OurPoker recipe no general component provides: the house rules file, the screen flow (home, name, lobby, seat, table, results) on web, Apple and Android, the poker table drawing (betting controls, hand text, showdown display, odds display), the wiring that selects the server components and connects them, the application's text in English, French, German and Spanish, the lessons, the icon and sounds, the desktop entry, and the end-to-end test specs. Facility `application`. It provides the poker game adapter; display-mode, video-calls and windows-desktop take their configuration in code (their `configuration` requirement is optional), so it provides no configuration port. The recipe's page, questions and component list are in `recipe.json`; the assembled application is built from the 39 components plus this one.

## User inputs
Eighteen settings, each with a default, adapted to aepm's grammars: `applicationId` (slug), `applicationName` (label), `packageId` (qualified), `scheme` (slug; the desktop URL scheme and native origin, lower case), `serverAddress`, `webAddress`, `inviteAddress` (address), `roomPrefix` (slug, ends with a hyphen), `modeEvent` (slug), `updatesEnabled` (boolean), `signingEnvironmentPrefix` (environment), `languages` (label: the languages answer, space-separated), and the six answers that change the house rules: `maximumPlayers`, `startingStack`, `levelSeconds`, `rebuysPerPlayer`, `decisionSeconds` (integers) and `computerPlayers` (slug: `none`, `on-request` or `fill-empty`, the computer-players component's `mode`). `server/src/rules.ts` writes those six over the house rules file when the server starts, and every component is built from the result, so the rules file stays the one source of the game's numbers; `recipe.json` sets the matching component settings from the same answers (`application.<setting>` targets). No secret is collected: accounts and keys are given by reference to the components that need them (server-host, ourapps-release, video-calls). The recipe's questions set `webAddress` (default `http://localhost:5173`), `serverAddress` (default `http://localhost:8788`, answered again after the server's first deploy), `inviteAddress` (when updates are on), `packageId` (when `bundleId` is answered; the default `app.ourapps.ourpoker` is the derived one) and the six rules answers. The Apple project folder is fixed as `OurPoker`: apple-host's `scheme` setting must be `OurPoker`, as `recipe.json` sets it.

## Artefacts and dependencies
`component.json` maps every implementation, build, rules, text, art, sound and test file to its place in the application (`server/`, `web/`, `ios/`, `android/`, `desktop/`, `rules/`, `resources/`, `verification/`); none goes under `components/`. The build files: `server/` package and lock (exact versions), `tsconfig.json`, `vitest.config.ts` and `src/env.d.ts`; `web/` package and lock, `index.html`, `vite.config.ts` (web-host's Vite configuration with the theme's colours) and `tsconfig.json`; `desktop/` package and lock; `ios/generate-project.ts` and `android/generate-project.ts` (apple-host's and android-host's renderers with their installed settings). The text the clients load is translations' generator output from `locales/strings.json`, written into `locales/generated/` by `scripts/make_component.py` and shipped: `web/src/strings.json` (the web client offers the languages of the `languages` setting from it), `ios/strings/Localizable.xcstrings` and `android/strings/values*/strings.xml`, which the Apple and Android `generate-project.ts` copy into the projects for the `languages` setting's languages only. Files that name a setting are templates (13); the installer's own substitution is run on each one by `scripts/make_component.py`. `dependencies` is empty: the code imports from 34 components by the paths `components/<name>/<platform>/...`, which exist only because the recipe's `components` list at exact versions put them there, so the layout is the recipe's, not this package's. Tools: node 26.5, python3 3.12, swiftc 6.4, kotlinc 2.2, java 26.0 (`tools.lock.json`; aepm matches an installed tool by these leading components). 50 artefacts carry `component: "ourapps-ae/<name>"` (android-host 1, apple-host 1, computer-players 1, guided-tour 5, store-update 11, video-calls 20, web-host 2, windows-desktop 9): the files whose imports or paths name an optional component, the desktop project files, the Swift and Kotlin modules that name its types (`Video`, `SeatScreen`, `Lessons`, `Updates`), and the web package files, which declare `livekit-client` for video-calls; each is installed only when the design includes the component (marked by `scripts/make_component.py`, checked by `authoring/check_conditional_artefacts.py`). 18 stand-ins under `implementation/stand-ins/` carry `withoutComponent` with the same name and the destination of the module they replace, and are installed when the design leaves the component out (computer-players 1, guided-tour 4, store-update 4, video-calls 8, web-host 1). Every design therefore installs one of each pair, and every client compiles.

## Provided interfaces
One standard document each in `interfaces/` describes them.
- `poker-game-adapter` (`ae/game-adapter`): `pokerAdapter(links)` in `server/src/adapter.ts`, turn-engine's adapter answering in the poker wire view (`server/src/contract.ts`, contract version 1) that the four clients decode. `recipe.json` connects this port to realtime-rooms' `game` requirement (the clients and the wire fixtures expect the poker view) and turn-engine's own adapter to this component's `game-adapter` requirement. `interfaces/poker-game-adapter.json` is an OpenRPC 1.3.2 document: `pokerAdapter`, `toWireView` and the fourteen `GameAdapter` members (every one but `view` is turn-engine's), with the wire view as JSON Schema 2020-12; `authoring/poker_game_adapter.py` derives it and `scripts/make_component.py` writes it.

## Required interfaces
Twenty ports, named by the type's last segment: `game-adapter` (turn-engine), `web-shell`, `apple-shell`, `android-shell`, `desktop-host`, `server-host`, `release-pipeline`, `invitations`, `display-policy`, `media-session`, `table-layout`, `card-graphics`, `chip-graphics`, `sound-cues`, `guided-tour`, `updates`, `controls`, `preferences`, `language`, `theme`. Seven are marked `optional`: `web-shell`, `apple-shell`, `android-shell`, `desktop-host`, `media-session`, `guided-tour` and `updates`, whose providers the recipe includes only for some answers (`includedWhen`); `recipe.json` drops the connection when the provider is left out. `interfaces/required-<port>.json` is a copy of the providing component's document. The server also composes seating, tournament, computer-players, holdem-rules, game-clock, presence, private-views, round-history, chip-ledger, level-schedule, rules-settings, card-deck, poker-hand-ranking, poker-odds, poker-strategy, guest-identity and room-directory by import, each through its own interface (`server/src/parts.ts`; guest-identity's `createIdentityApi()` is passed to seating and, as `services.identity`, to realtime-rooms in `room.ts`); those are listed in `recipe.json`, not here, because they are reached through turn-engine's parts rather than a port of this component.

The server wiring has no adapter between a provider and its consumer: game-clock, private-views, presence, round-history, chip-ledger, level-schedule, holdem-rules, poker-strategy and rules-settings provide the operations turn-engine, tournament and computer-players declare. The `// GAP:` marks are in the Apple and Android clients and are rows of `INTEGRATION-GAPS.md`.

## Integration
See `INSTRUCTIONS.md` for what to select and configure, and its part 3 for the commands that build and run the installed application.
- web-host: `web/vite.config.ts` returns `webHostConfig` from web-host's installed `web/vite.ts` with its rendered `web/settings.ts` and the theme's colour table; web-host injects the page head and writes the manifest, service worker and headers into the build. `web/index.html` holds the page body and the entry `src/main.ts`.
- translations: the generated text files are shipped (see above); `web/src/i18n.ts` offers the languages of translations' rendered `web/languages.ts`; the native pickers offer the application's `languages` setting, and their projects carry only those languages' text.
- apple-host: `ios/generate-project.ts` runs apple-host's `renderApple` with its rendered `apple/settings.ts`, the Swift folders of the installed components, LiveKit when video-calls is installed, and the server address; XcodeGen then writes the project. The scheme is `OurPoker`; sounds (and any pictures a developer adds) are in the project's `Art` folder (folder reference).
- android-host: `android/generate-project.ts` runs android-host's `renderAndroid` with its rendered `android/settings.ts`: activity `app.ourapps.ourpoker.MainActivity` (the Kotlin package is fixed, not the package id; every string and resource is looked up by name so no source names the package id), the Kotlin serialization plugin, `INTERNET` and with video `CAMERA`, `RECORD_AUDIO` and `MODIFY_AUDIO_SETTINGS`, and the installed components' `android` folders. Sounds are `res/raw/snd_<cue>.wav` and the manifest `res/raw/sounds_manifest.json`; lessons `res/raw/lessons.json`; pictures a developer adds `res/drawable-nodpi/`.
- server: aepm renders `components/server-host/server/host-settings.ts` and `wrangler.jsonc` from server-host's settings; `server/src/index.ts` is the worker module both run: `npm start` runs it on Node through server-host's `start.ts`, `npm run deploy` deploys it to Cloudflare with the rendered `wrangler.jsonc`, and `npm test` runs the room tests in the local Workers runtime with the same configuration.
- desktop: `desktop/src/main.cjs` calls windows-desktop's `start` with `desktopConfiguration(app)`; `npm run build` builds the web client in desktop mode.

## Visual definition and connected examples
`visual/definition.json` maps the one output and twenty inputs (seven optional) to the interfaces above and lists the eighteen settings. `visual/examples/connected.json` connects it to one stand-in for the rest of the application; the 39 components are drawn in the recipe page. Both image formats and a text description are in `visual/output/`. The generated diagram's DOCTYPE line is removed from the SVG for the catalogue (INTEGRATION-GAPS.md G7.17).

## Infrastructure
No service is deployed by this package and no account is needed to hold it. The servers, hosting, video and release accounts belong to server-host, video-calls and ourapps-release. Costs are unmeasured.

## Verification
`node --test tests/portable.test.ts` (required, package root) checks: the house rules file against its schema and the blind table; every string in four languages with identical placeholders; every lesson step's keys and the lesson ids the code asks for; every string key the screens name; the asset list against the files (sizes, hashes, under 5 MB, generic names); the sound and art manifests; the manifest's file list, destination map and template tokens; component paths the code imports; the wire fixtures; the configuration example (`examples/configuration.ts`).
Not run here: the end-to-end specs under `tests/e2e/` (server hand, two-player browser hand with a public display, reconnect, update, media, native hand-offs, Windows package). They need the assembled application and its harness. The recipe repository's `authoring/try_install.py` installs designs with aepm and builds them: server and web type-checked, server tests run, the web client loaded in a browser, the Apple schemes built for the iOS and tvOS simulators. The Kotlin is not compiled for Android there (no Android SDK); `authoring/kotlin-stand-ins` type-checks the Kotlin stand-ins on the JVM. The package's own suite does not compile against the components.

## Scenarios and presentation
Two people sit, the host starts, the player to act folds and the hand ends with every chip counted (`tests/e2e/server/hand.test.ts`). Two browsers play a hand with a public display showing the table and no private cards (`tests/e2e/web/browser.mjs`). A phone loses its connection and rejoins by name with a fresh view (`tests/e2e/web/session.test.mjs`). The connected diagram shows the application taking the shells, facilities and presentation components and giving the poker adapter back.

## Updates and removal
Patch updates replace files; no data is kept, so there is no `migration.json`. Removal deletes the owned files listed in `component.json`; the application's seats, tokens and stored preferences live on the server and the devices and are not touched.
